# Dependencies and lock files

Read this before adding, bumping or removing a package, or when the CI lock job, a hashed
install or `tests/test_lockfile.py` fails.

Contents: the files; regenerating the locks; what catches what; installing per OS; recipe: add,
bump or remove a package; optional packages; native libraries; upgrade notes.

## The files

| File | Holds | Installed by |
| --- | --- | --- |
| `requirements.txt` | the direct runtime dependencies pinned with `==`, plus `posthog<4` | developers on macOS and Windows, together with requirements-dev.txt |
| `requirements-dev.txt` | pytest and ruff only | the same |
| `requirements.lock` | requirements.txt fully resolved and hashed | the image (`Dockerfile` builder stage) |
| `requirements-dev.lock` | both files fully resolved and hashed | CI's test job; Linux developers who want CI's exact set |

- `posthog<4` stays with its comment: chromadb 0.4.24 requires only posthog>=2.4.0, and posthog 4
  changed `capture()` so every startup logged a telemetry error.
- Both locks are generated by uv 0.12.5 (`UV_VERSION` in `.github/workflows/ci.yml`) for linux /
  CPython 3.10 with `--generate-hashes --no-strip-extras`; line 2 of each records the command.
- They are linux resolutions: no environment markers, uvloop pinned unconditionally, Windows-only
  packages such as colorama absent. Install a lock directly only on Linux with Python 3.10.
- The runtime lock never contains pytest or ruff, and the dev lock is a superset of the runtime
  lock with identical shared versions; both rules are tested.

## Regenerating the locks

1. `uv --version` must say 0.12.5. CI installs it with `pip install "uv==0.12.5"`; any install
   works, including the Windows `uv.exe`, which produces byte-identical locks.
2. From the repository root, compile into the existing files:

```bash
uv pip compile requirements.txt --python-platform linux --python-version 3.10 --generate-hashes --no-strip-extras --output-file requirements.lock
uv pip compile requirements.txt requirements-dev.txt --python-platform linux --python-version 3.10 --generate-hashes --no-strip-extras --output-file requirements-dev.lock
```

3. Read `git diff -- requirements.lock requirements-dev.lock`: the intended packages and their new
   transitive dependencies, nothing else. A second run must leave no diff.

Why exactly these commands:

- Compiling into the existing files makes uv treat their pins as preferences, so an unrelated
  upstream release does not move other packages. That is what lets the CI lock job recompile and
  diff without failing at random.
- uv records the command line in line 2 and the CI lock job diffs the whole file: reordered
  flags or a `./` path prefix change that line and fail CI while `tests/test_lockfile.py` still
  passes. `--quiet`, which CI adds, is not recorded.
- `--no-strip-extras` is load-bearing. Without it the lock records plain `uvicorn==...`, and
  `pip install --require-hashes` refuses chromadb's `uvicorn[standard]` requirement with "all
  requirements must have their versions pinned with ==".

## What catches what

| Check | Catches | Misses |
| --- | --- | --- |
| `tests/test_lockfile.py` (offline, needs no uv) | a header without the target flags; an entry not pinned with `==` or without well-formed hashes; a direct requirement missing from a lock or locked at a version its specifier rejects; a dev lock that is not a superset of the runtime lock or disagrees on a shared version; stripped extras; posthog 4 or later; pytest or ruff in the runtime lock | a requirement removed from a requirements file; a hand-edited transitive pin; reordered header flags |
| CI lock job | any difference between the committed locks and a fresh compile | whether the resolved set works |
| CI test job | a lock that `pip install --require-hashes` refuses; lint; the suite on the locked versions | the image, Compose |
| CI docker job | the image builds from `requirements.lock`, contains no compiler and boots to GET /health | /ready, the volumes, frontend, bot |

## Installing per OS

| Where | Command | Versions |
| --- | --- | --- |
| Linux, Python 3.10 | `pip install --require-hashes -r requirements-dev.lock` | exactly CI's |
| WSL, Linux venv | `uv pip install --python ~/.venvs/<name>/bin/python --require-hashes -r requirements-dev.lock` | exactly CI's |
| macOS, Windows | `uv pip install -r requirements.txt -r requirements-dev.txt -c requirements-dev.lock` | every shared pin matches the lock; on Windows colorama and pyreadline3 are added and uvloop is dropped |
| anywhere, no constraints | `pip install -r requirements.txt -r requirements-dev.txt` | direct pins only; transitive versions float |

- After the locks change, rerun your install command. On Linux,
  `uv pip sync --python <python> --require-hashes requirements-dev.lock` makes the environment
  exact again: it also removes packages the lock does not list, which `uv pip install` never does.
- A green run in a floating environment does not prove CI is green.

## Recipe: add, bump or remove a package

1. Edit `requirements.txt` (runtime; pin with `==`; a comment for any unusual constraint) or
   `requirements-dev.txt` (test and lint tools only; they must never reach the runtime lock).
2. Regenerate both locks as above and read the lock diff.
3. `pytest tests/test_lockfile.py -q`.
4. Refresh your environment from the new lock (Linux, WSL) or the requirements files (macOS,
   Windows), then run the tests for the code that uses the package and the full suite.
5. A native runtime library goes into the runtime stage's apt-get line in `Dockerfile`, build
   tools only into the builder stage. Build the image if Docker is available: the CI docker job
   is otherwise the first place a missing system library shows.
6. Removing a package: delete its imports and uses too. Your venv still has the package, and
   ruff does not check what is installed, so a leftover import can pass locally and fail in CI
   and the image. `tests/test_lockfile.py` does not notice a stale lock entry; the CI lock job does.
7. Commit the requirements file and both locks in one commit.

## Optional packages

A package in neither requirements file is in neither the image nor CI. Import it lazily or
behind `try`/`except ImportError` and degrade visibly. The pattern is in `app/rag/reranker.py`: a
module-level `try: from flashrank import RerankRequest` with a fallback class, and a lazy
`from flashrank import Ranker` in `FlashRankReranker._get_ranker` that logs a warning and falls
back to no reranking. flashrank itself is still undeclared, so RERANKER_PROVIDER=flashrank
reranks nothing in the image or in CI; see KNOWN_ISSUES.md, section Models, keys and reranking.
To make an optional package real, declare it in `requirements.txt` and regenerate the locks.

## Native libraries

- The runtime stage installs only libgomp1, which onnxruntime (pulled in by chromadb) links
  against. A package with another native runtime dependency adds it to that apt-get line.
- Compilers and headers belong in the builder stage, where build-essential already is; the CI
  docker job fails with "gcc is present in the runtime image" otherwise.

## Upgrade notes

- chromadb: `tests/conftest.py` `_release_chroma` reads the private
  `SharedSystemClient._identifer_to_system` (the typo is chromadb's) to stop the clients each test
  opened, which once exhausted file handles on Windows. An upgrade can break every test at setup.
  Re-check the posthog constraint at the same time.
- uvicorn: keep the `[standard]` extra. It brings watchfiles, which `--reload` uses, and uvloop,
  and `tests/test_lockfile.py` expects at least one extras requirement.
- ruff: the version in `requirements-dev.txt` is what CI runs, and a new version can sort imports
  differently. Bump it in its own commit together with the resulting fixes.
- Any upgrade: the CI lock job proves only that the locks match the requirements files, not that
  the new set works. Run the full suite on the new lock before committing.
